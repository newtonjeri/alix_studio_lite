# Lite UI (ASL, V32) — front-end contract

Last updated: 16 October 2026.

The Lite UI is the designer's **ASL FINAL Template V32** (product name ASL): one HTML page and a developer handoff, kept verbatim in `docs/reference/ui_v32/` with the owner's feedback on the V19 build (`UI_Feedback_changes_v1.pptx`, 14 October) and the trajectory processor the Tune stage is to copy (`Alix_Studio_Lite_Trajectory_V2.html`). It replaced V19 on 14 October (V19's files stay in `docs/reference/ui_v19/`). The UI built before V19 is **Legacy Lite**: it stays at `/legacy/` (`tools/run_lite.sh --ui legacy`) and is tagged `legacy-lite-0.1` in git.

**The owner's changes of 14 October** (the feedback deck and the answers to it):
- The 3D scene is only where motion is shown: Tune's simulation beside the plot, the Trajectory Viewer, the full sequence, the single-arm simulation and V32's transition runs (since feedback v5 also Save & Review, S1's merge review and S2's simulation). Everywhere else the page shows its own region images from the slides: the arm cards, the zoom, Drag & Teach, Home, Setup & Safety, the Project Summary.
- No STOP BOTH on the log-in screen; notifications stay 15 s and are coloured by their level (green a success or a good status, orange a warning, red an error; the owner, 20 Oct); Robot & mode has Connect all and Disconnect all; every trajectory file name in a project is used once; Save & Review has no playback section.
- Prepare can be opened again after teaching, for the same arm: what was forgotten is set there and carries on to the later stages.
- Tune + Simulation is laid out as the Trajectory V2 processor: its six steps, its automatic optimisation, a plot tooltip with every joint and the line, its plot tools and Play / Pause / Restart, with the 3D beside the plot (Review: the recording; Compare: the tuned file).
- The controller's global points (search, MoveJ / MoveL) are in the start-pose lists and in Advanced, the controller's programs are a list in Advanced's RUN tab, and the upload shows a progress bar.
- The Activity Logs page reads the server's logs: the page's own events with every request, job result and controller command.
- Prepare's Task Transition & Start Point Tools are connected: transition trajectories kept in the project, simulated in 3D and run on one arm alone; start points captured from the controller or taken from a file's last line, and moved to.
- Save Project Folder writes the real files: everything Lite's server keeps for the project, with the page's manifests (the UGV position and the start points and transitions in them) and the project's audit trail.
- V32's new workflow features are all connected.

**The owner's changes of 15 October, later** (`UI_Feedback_changes_v3.pptx`, slides 1–7, and the owner's notes on them):
- Tune is the trajectory HTML's front end as it is (`docs/reference/ui_v32/Alix_Studio_Lite_Trajectory_V2.html`): its six steps with its fields, labels, buttons, tables, messages and defaults (sample interval 5 ms, idle rolling window 11, idle threshold 8 counts/sample, minimum idle run 20, mean smoothing window 101; Trim, Mean Smooth and Scale on; "Algorithm used"); its Analyze table and figures; its Review playback, plot (the file's own values against the row number), box-select and manual rows, regions table; its Generate figures, message and three downloads under its names (`<recording>_trim_mean_scale_processed.txt`, `…_processing_report.json`, `…_processed_J1_to_J7.png`); its Compare with an optional external file, its figures, one synchronized time cursor on two plots, and its regions table. Lite adds the robot in 3D beside the plots (moved by the HTML's Play / Pause / Restart and timelines), the limits, keeping the file in the project for Real Test, and Analyze's optimised time. V32's own tuning cards (the smooth window per selection, Trim Selected Region, Apply Tuning) are gone. The sample interval stays 5 ms (Lite's one clock), Step 1 is the region's recording, and file times are (N − 1) × 5 ms as everywhere in Lite.
- Manual tuning is the default and is the HTML's algorithm itself (`optimise/manual.py`): its output is byte for byte the HTML's (checked in Chrome on the HTML's own functions; `tests/test_manual.py` holds the hashes). Lite's earlier changes to it are gone (mirrored ends, the 0.25 s blend at region edges, the 41-line window), and nothing stretches the file to the limits any more: that stretching made a 15 s target come out at 36 s (slide 5). The limits L1–L6 are checked and shown, never enforced ("the hardware decides"): a manual file is kept, uploaded and run whatever they say; sending one that breaks a limit asks once (`code: "limits"`, then `limits_seen`), as do merges.
- Time-optimal (TOPP-RA) is the other choice in Setup, separate on the server (`optimise/engine.py`): ALIX's chain on the recording as taught, the fastest time within the limits or a longer target; it never goes through Trim, Mean Smooth, Scale, the suggestions or the scale regions (Analyze and Review are closed for it), and its limits stay enforced.
- Analyze's optimised time is fitted to the generated file: the suggestions scaled together (each a whole percent, 1–300 %) so that after the region's Trim the file comes to the time asked (`analysis.fit_target` with `manual.trimmed_counts`).
- Real Test shows the file it sends: its name above the gates and under Upload.
- Prepare: Apply beside the pole moves the pole alone and Apply beside the hand the hand alone (the pole's Apply staged the hand too); a held channel keeps what it reads (`POST …/setup {kind}`, `robot.stage_part`). A new hand preset, Cleaning Pose (Little, Ring, Middle, Index 1000, Thumb Bend 0, Thumb Rotate 1000), in Prepare, Advanced Robot Controls and the stage dialog (`staging.PRESETS["CLEANING"]`). The Custom hand channels have their own Apply (the hand only).
- Drag & Teach: the voice counts every second until STOP DRAG, past the target, and no longer says "Target time reached" (the screen still shows the target).
- Prepare: each Apply turns green, "✓ Applied", once its value is on the arm (the server marks it inside the move's own job, so it is marked when the job reports done; "Applying…" meanwhile), and reads "Apply" again as soon as the pole height, the preset or a channel on screen differs from what was applied (the owner, 15 October).
- Real Test: "Teach another task →", greyed out until this region's file is on the controller (uploaded, or its test run completed: the region's status), lets go of the arm and opens the next task of the queue at Prepare (the owner, 16 October: it went back to the same task), on the same arm when that task uses it, else on its other arm; a task with nothing to teach in Release 1 is passed, and after the queue's last task Prepare opens with the Operator Journey to choose. The file stays on its program, and PASS still approves the region (the owner, 15 October). Under Upload it also names the program as the controller keeps it (`<region>_<version>`, at most 32 characters).
- Prepare (15 October, the owner again after the review): the pole's Apply moves the pole only (the pole's own move at 50 %, read back, as Advanced's pole control) and the hand's Apply the hand only; neither touches the other part, and each stays "✓ Applied". The pole's Apply no longer asks whether to use the hand for the recording. A held hand channel is refused when the controller's hand reading is missing (it used to take a remembered value).
- Tune, checked against the HTML (15 October): the fields keep what is typed and are read the HTML's way when a file is made (`getParams`: a window odd and at least 3, empty or 0 its default, a negative threshold 0, the minimum run rounded); a region's scale as the HTML takes it (empty or 0: 100 %, at least 1 %; Lite refuses above 10,000 %, which the HTML does not limit). A field or a region's scale being typed is never overwritten by the server's reply to an earlier change; a region's scale is saved when it is committed (Enter or leaving it); Generate, keeping and another arm step wait for a change on its way. The scale regions belong to the recording they were set on: another recording (taught, loaded or chosen) starts without them, one undo step back, as the HTML clears them with every file. Settings saved for Lite's earlier algorithm read as manual tuning with the HTML's smoothing window, so that algorithm's file is no longer current. The processing report has the HTML's keys (`selectedStages.meanSmooth`, `generatedAt` as `toISOString`, `automaticOptimizationAnalysis` as made with the file); the processed TXT downloads with LF line ends; seconds are written with `toFixed`'s rounding. Also as the HTML: Reset (regions, analysis, comparison and playback cleared, every stage checked, one undo step), "Pipeline complete" as a status, its status lines while processing and after a stage change, Review and Compare each at their own moment, the analysis's fitted time withdrawn once a suggestion or Trim changes, and the plot PNG in its joint colours on white in either theme.
- The speed slider (top bar, beside the mode pill; slide 1 and the owner's notes): one speed, 1–100 %, for every MoveJ / MoveL Lite sends on both arms — a move to a start or a start point, a move to a global point (Prepare, Setup & Safety, Real Test, Advanced, the run section), and the controller's own move to a program's first point; the 3D's moves follow it (`staging.move_fraction`), and Advanced's point Speed % shows it. `GET|POST /api/robots/speed`, also in `/api/robots/status`. Each move goes ALIX's way: the controller's global speed at 100 % for the move, the move at the slider's %, then the global speed put back (ALIX's `global_speed_guard` and `park_arm`; the control program's runner restores it in its `finally`, a failed run included). The speed put back is the one found when the arm was connected: the controller's program state is read for it (`plan_speed`), and when the controller does not report it — ALIX's finding F98, and its hardware run records show the field empty whenever no program runs — 50 % is taken, the value ALIX and the runner always leave. It is also put back when an arm is disconnected and when Lite closes; a linked arm is let go only when nothing runs on it (STOP first), so a move's own `finally` puts the speed back on an open link. The slider starts at the first connected arm's found speed. A plan's 3D frames keep the speed the plan was made at (`move_pct`), and the plans and the 3D are made again when the slider moves. (ALIX notes an exported `libalgo_get_rt_global_ratio` that might read the pendant's ratio; it is untested on hardware and not used.)

## How the page is connected

- **`web/index.html`** is the designer's file, byte for byte, plus one marked block at the end that loads `web/lite/`. `tests/test_lite_ui.py` enforces this. A new designer version therefore drops in as a file swap.
- **`web/lite/`** is Lite's bridge. It replaces the page's template functions, one group per file, with versions that call the backend. It keeps the page's own screen updates.
  - The same test fails if a function the bridge replaces is renamed or removed in a new version.
  - The bridge uses only the page's colour variables, so the light and dark themes both apply. The page's own dark theme is incomplete (defect D5); `lite/dark.css` completes it.
- **`/api/*`** is the Lite UI's API (`server/api_v2.py`). It is named after the handoff's suggested boundary (section 17).
  - Every route needs the session from the log-in, except the log-in itself, STOP, and `GET /api/lite/hello` (how a second start of Lite finds the one already running).
  - Legacy Lite keeps `/api/lite/*` and asks for the same operator PIN; its engineer level, like the Lite UI's, belongs to the session that entered the PIN. Both share one backend, so one robot, one E-stop state and one STOP.

## The gates on every execution

Checked by the server on every execution, in the 3D simulation, in Hardware sim and in Real; the page only shows them (`server/api_units.py`, `identity` and `gates`):

1. **Arm.** A trajectory runs only on the arm it was taught on. Every recording, tuned candidate and kept version carries `taught_arm`; a file of the other arm, or of an unknown arm, is refused (`code: "arm"`): it is never shown moving, tuned, uploaded or run there. A loaded file's arm comes from its name (`L_`, `R_`, `LEFT`, `RIGHT`) or is stated, and a name and a statement that disagree are refused. An older recording without a recorded arm gets one back only when its bytes are a built-in file's.
2. **Stage.** Every file carries the pole height and hand pose it was taught with (`stage`). Every execution sets them first: the pole (ALIX's measured travel time), then the hand (ALIX's hand units and speed), each read back (pole within 5 mm, every set hand channel within 30 counts), then the joint move to the first line, then the trajectory. If the pole or the hand does not arrive, the job ends there and the arm never moves. A file without its stage is refused (`code: "stage"`) until the operator states it; a recorded stage is never overwritten.
3. **Limits.** A run needs a kept version that passes L1–L6. L3 reads acceleration as ALIX does: the 20 Hz zero-phase band-limited second difference (`plan_min_time.band_limited_util`, finding F99c), never raw differences, which read the recorder's millidegree steps as thousands of °/s². FILE_04 as taught: 757 °/s² band-limited (ALIX's own function gives the same), 13,800 raw.
4. **Robot.** Hardware sim or Real, a Real motion confirmed, no motion on either arm while an E-stop is not clear; STOP always works. **Hardware sim moves nothing physically** (D30 as clarified on 13 Oct): programs run in the controllers' SIM mode and the pole and the hand are emulated, so drag teaching needs Real, and a recording as taught never plays back on the real arms.

The 3D simulation plays the same execution the robot does (`GET …/timeline`): ALIX's FK poses every link below the sliding plate at each instant, so the arm is drawn at its stage height, not at the standing pose's.

## The live link to the arms (read only)

`run_lite --robot realman` connects each controller through ALIX's own robot I/O code (`alix_dispatch.connect.open_arm`) and reads, about five times a second, the three devices of each side: the arm (seven joints, error codes, the controller's run mode), the pole (`peripherals.Pole`) and the hand (`peripherals.HandModbus.read`, ANGLE_ACT), and the E-stop input IO3, wired normally-closed to ground, so 0 is pressed (`server/robot_link.py`). Robot & mode shows it, and the live E-stop drives the interlock (unreadable or not in mode 5 blocks motion, like a press). **Lite commands the linked arms** (decided 14 October), through ALIX's own robot code (`server/robot_real.py`): in Real, Prepare's Apply stages the pole and then the hand at 50 % speed, each read back (`staging.stage_arm`); drag teaching runs on the controller and STOP DRAG saves the controller's own recording into the project, byte for byte as the control program saves it; upload, the program list and runs use the control program's own tool, `vendor/control_app/rm_upload.py` (the upload reads the stored size back, tried again if the controller does not answer at once; the run lets the controller move to the first point at 20 % and watches its error codes), with the controller's REAL mode set and read back, then put back; a hand that settles on the tool counts as done, the control program's own rule (`vendor/control_app/hand.py`: arrived or settled); Move to Recorded Start moves to the file's first line at 30 % (`staging.park_arm`). In Hardware sim the controller runs the program in its SIM mode and the pole and the hand, which it cannot simulate, are taken as arrived. While a command runs, the link does not read at all, so two callers never compete for a controller. The end of a long command (a program run, an upload, a saved drag take, a MoveJ) counts as fresh for a second, until the first reading after it lands; a controller that then stays silent is stale as before (the lab's logs of 16 October showed some 55 false "No fresh reading" alerts in that moment). The status log records the verdict (`stale`). Every command is in the hardware log with its return code. Checked end to end against ALIX's emulated arms (`tests/test_robot_real.py`, drag teaching added to the emulator as the control program uses it); not yet on the robot: the 50 % pole and hand speeds and the stop of a running program are new on hardware. The one setting the link itself writes is the end port's Modbus mode, which reading the hand needs (the control program and ALIX set it the same way). **STOP acts like the E-stop** (decided 14 October): STOP BOTH sends each linked controller ALIX's stop the E-stop's way (`staging.stop_devices(hard=True)`: `rm_set_arm_stop`, `rm_set_lift_speed(0)`, the hand frozen at its measured angle), both at once, then ALIX's check that the arm is still (`track.stop_program`); one arm's STOP uses the slow stop on its path. Any STOP holds the connected arms until Recover (the chip reads "Stopped by STOP: press Recover"), on the stand-in too. A controller that does not confirm the stop is reported as an error. The red E-stop buttons remain the safety stop. The link needs Linux (the RealMan SDK ships for Linux only); elsewhere Connect says so. `--robot emulated` gives the same link to ALIX's emulated arms.

## While the robot is a stand-in

- Nothing moves. Prepare and the region steps say "read back" as the real backend will; Real Test and Advanced Robot Controls add that nothing reached a controller. The arms start at the robot model's standing pose (pole 300 mm, hand open), as the 3D view does.

- Start-pose profiles are names only; stored poses come with the robot I/O backend.
